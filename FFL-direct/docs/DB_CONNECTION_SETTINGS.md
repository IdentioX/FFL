# Настройка Direct MySQL в приложении

Версия: 0.3.1-dev (6). Runtime-профиль проверен на двух настоящих локальных MariaDB. Регрессия завершена с результатами, указанными ниже и в evidence.

Новый запрос пользователя разрешает runtime-настройку Direct MySQL. Прежний запрет на экран подключения и правило «только BuildConfig» относятся к предыдущим этапам. FastAPI, HTTP, backend IP и JWT не возвращены.

## Использование

На чистой установке: «База данных не настроена. Настройте подключение для продолжения» → «Настроить подключение». После настройки: вход водителя → «Настройки» → «Подключение к БД». При недоступной БД редактор также доступен через ссылку администратора на экране входа.

Нужны host/DNS или IPv4, порт (3306 по умолчанию), база, отдельный пользователь с минимальными правами, пароль и доверенный CA-сертификат PEM. Значения из макета не являются конфигурацией. Имена `root` и `admin` отклоняются. Наличие другого имени само по себе не доказывает минимальные права: их обязан назначить администратор MariaDB.

TLS 1.2/1.3, `verify-full`, проверка CA и имени сервера обязательны. Отключение TLS и `trustAll` отсутствуют. Публичная сеть, firewall и доступность корпоративной БД автоматически не изменяются. IPv6 и JDBC URL с параметрами текущий валидатор не принимает.

«Проверить соединение» использует введённый черновик: реальный JDBC handshake, выбор указанной БД, проверка catalog и `SELECT 1`. Соединение закрывается. Изменение любого поля сбрасывает подтверждение; сохранить непроверенный черновик нельзя. Сохранение повторяет проверку непосредственно перед применением. Ошибка не заменяет действующий профиль. Отмена черновика ничего не сохраняет. После нажатия «Сохранить настройки» и успешной повторной проверки начатое атомарное применение доводится до конца; закрытие редактора не откатывает уже начатую запись.

Все сетевые операции проходят через существующий IO boundary: Dispatchers.IO/runInterruptible; connect timeout 3 с, socket timeout 5 с, query timeout 3 с, общий лимит операции 15 с. Отмена прерывает корутину; завершение некооперативного JDBC ограничивается драйверными таймаутами. SQL-ошибки выводятся как фиксированные сообщения без vendor text, реквизитов и stacktrace.

## Хранение и применение

Весь профиль хранится в `noBackupFilesDir/direct-profile-v1.enc`: AES-256/GCM с новым случайным IV и authenticated associated data. Ключ создаётся в Android Keystore и не экспортируется. AtomicFile записывает только шифротекст. Профиль исключён из резервного копирования; allowBackup=false уже действовал в приложении. DataStore сессии не содержит DB-пароль.

Сохранённый профиль приоритетнее BuildConfig. BuildConfig оставлен как совместимый исходный профиль для прежних приватных тестовых сборок; выдаваемый APK содержит пустые DIRECT_MYSQL_* и настраивается через интерфейс. Повреждённый/недоступный зашифрованный профиль приводит к закрытому состоянию без скрытого возврата к другому серверу.

После успешной проверки и атомарного сохранения старый граф помечается недействительным: его connector закрывает все зарегистрированные соединения и запрещает новые. Сессия инвалидируется, прежняя публикация сессии дожидается завершения, worker и уведомления отменяются. Новый граф создаёт зависимости с новым профилем; UI получает новый ключ ViewModel. Повторный вход обязателен. SQL бизнес-операций не переписывается.

Сессия помечена идентификатором профиля. Порядок, дата, прокрутка и состояние уведомлений хранятся в отдельном namespace профиля: SHA-256 от host/port/database/user/CA. Пароль в идентификатор не входит; его замена сохраняет порядок. Изменение сервера/базы/учётной записи/CA изолирует данные. Цифровые ID водителей разных серверов не дают права восстановить чужую сессию.

## Границы защиты

Первоначальная настройка разрешена на ненастроенной установке. Повторный доступ к сохранённому профилю требует системного подтверждения PIN/пароля Android; при отсутствии защищённой блокировки редактор закрыт. Это проверка владельца устройства, а не серверная роль администратора. Для выделенных устройств нужны управляемая политика и контроль доступа к самому телефону. Очистка данных/переустановка сбрасывает локальные ограничения.

Пароль не подставляется в видимое поле, не сохраняется в savedInstanceState и не передаётся в логи/аналитику. Пустое поле сохраняет имеющийся пароль; отдельная кнопка показывает только вновь введённое значение. Экран использует FLAG_SECURE и закрывается при уходе приложения в фон. Публичные снимки сделаны с вымышленными данными через отдельный instrumentation-сценарий без настоящих реквизитов.

Keystore защищает данные на диске. Работающий Direct-клиент должен иметь возможность расшифровать пароль; защита не исключает извлечение из скомпрометированного процесса/root-устройства. Аппаратное хранение на физическом телефоне не проверено; эмулятор не доказывает его наличие. Общий DB-пользователь не обеспечивает серверную изоляцию строк водителей. Прежний `DRIVER_ROLLOUT=BLOCKED_SECURITY` не снимается этой функцией.

## Команды воспроизведения

В подготовленной Linux-среде (`source /workspace/.ffl/env.sh`, `cd /workspace/FFL-direct`):

```bash
bash gradlew --offline --no-daemon --max-workers=2 :app:assembleDebug :app:testDebugUnitTest :app:lintDebug :app:verifyDirectRuntime :app:assembleDebugAndroidTest
bash gradlew --offline --no-daemon --max-workers=2 :app:assembleRelease
python3 tools/run_runtime_connections.py --serial emulator-5558 --synthetic-state /workspace/.ffl/direct-dev --restored-state /workspace/.ffl/direct-restored --output /private/NEW-runtime-checks
FFL_DEV_STATE_DIR=/workspace/.ffl/direct-restored python3 tools/dev_database.py test-restored --serial emulator-5558 --runtime-profile
```

Выходной каталог должен быть новым и находиться вне проекта. Первый runner очищает только Direct-пакет на явно выбранном выделенном эмуляторе; реальная конфигурация инжектируется только в приватные test files и удаляется после выполнения. После его успешного завершения активен профиль восстановленной локальной БД. Второй runner сохраняет runtime-профиль и проверяет точный установленный публичный APK, вместо пересборки с реквизитами.

UI без БД: `tools/run_design_android.py --serial emulator-5558 --output /private/NEW-ui-checks --classes ...`. Этот runner очищает приложение; запускайте после DB-регрессии. Список выбранных классов и точные команды сохранены в safe summary evidence. Семь отрицательных JDBC/TLS-проверок требуют локального `tools/p2_tls_fixture.py` на19061–19064 и соответствующего test CA. Wire fixture не является успешным MySQL-сервером.

`python3 tools/verify_runtime_connection.py` сверяет уже собранные результаты, число тестов, SHA установленного APK и исходников; сам тестов не запускает. Старые аудит-валидаторы относятся к0.2.2 и не используются для подтверждения0.3.1.

## Среда и ограничения проверки

API30 / Android11, программный x86_64-эмулятор без KVM,360×800dp и320×640dp. Из-за медленного программного рендеринга системный `ro.hw_timeout_multiplier` установлен в5: порог Android ANR увеличен, сетевые таймауты приложения остались3/5/3/15с. Это ограничение стенда явно сохранено в summary. Холодный запуск проверяется по реальному foreground accessibility-экрану и отдельному тесту расшифровки/SELECT1; истечение display-wait у `am start -W` не считается быстрым успешным запуском.

Реальный телефон, Android24/36, аппаратный Keystore, успешный ввод системного PIN, Windows и периодическое поведение WorkManager в Doze не проверены. Текущий release APK собран с R8, но runtime0.3.1 на release отдельно не запускался. Исторические minified PASS0.2.2 не переносятся на эту версию.

## Воспроизведение проверки системного уведомления

Для plain instrumentation-теста уведомлений на этом API30-стенде требуются стандартные системные анимации (`animator_duration_scale`, `transition_animation_scale`, `window_animation_scale` =1). Прежний исходный прогон с0 сохранён как NEGATIVE. Это не сетевой timeout; данные уже были получены ViewModel. Не скрывайте этот отказ и не переносите его на результат другого режима.

Независимая проверка с0 выполняет реальные Worker/SQL-счётчики и подготовку уведомления, завершает instrumentation, затем нажимает настоящий элемент в шторке ОС и проверяет обычный MainActivity/новый заказ. Setup-метод явно помечен fixture-only; его JUnit PASS сам по себе не доказывает переход.

```bash
# На выделенном эмуляторе с уже настроенным восстановленным профилем:
python3 tools/run_native_notification.py --serial emulator-5558 --state /workspace/.ffl/direct-restored --output /private/NEW-native-notification
```

Точные значения системных анимаций сохраняются в summary. Фактический PASS получен с0 для всех трёх. Во время host-нажатия instrumentation уже не выполняется. Снимок содержит только вымышленные зарезервированные строки, но данные загружены из реальной MariaDB текущим APK. Native readiness подтверждена за45.94с на медленном программном стенде; это не измерение производительности физического телефона.
