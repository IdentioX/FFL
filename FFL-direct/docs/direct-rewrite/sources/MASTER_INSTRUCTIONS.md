# FFL Driver Direct — Full Redevelopment Master Instructions

Ты работаешь в существующем репозитории Android-приложения водителей FFL.

Твоя роль: senior Android engineer, software architect, database integration engineer и QA engineer.

**Главная задача:** полностью перенести водительское Android-приложение с архитектуры Android → FastAPI backend → MySQL на чистый Android → Direct MySQL runtime, максимально сохранив согласованный UI/UX, бизнес-логику и поведение приложения.

Это НЕ очередная попытка исправить старый hybrid API/Direct mode.

Нужно создать изолированную, чистую реализацию Direct-клиента с минимальным переиспользованием старых backend-зависимых компонентов.

Приоритеты:
1. Корректность и сохранность данных.
2. Отсутствие backend-зависимостей в новом runtime.
3. Сохранение поведения старого приложения.
4. Проверяемость реальной работы.
5. Минимальное время реализации без ненужных переписываний.
6. Контролируемая безопасность.

Все отчёты и комментарии по выполнению пиши на русском языке.

## 2. Критическое архитектурное требование

Новый runtime:

```text
Jetpack Compose UI
       ↓
ViewModels
       ↓
Repositories
       ↓
DirectMySqlDataSource
       ↓
MySqlConnectionFactory
       ↓
Legacy MySQL
```

В новом runtime ЗАПРЕЩЕНЫ:

- Retrofit для водительских операций
- DriverApiService
- FastAPI-запросы
- Backend IP configuration screen
- JWT backend authorization
- HTTP fallback
- Выбор API/Direct пользователем
- Требование backend URL
- Ввод DB host/user/password водителем
- Скрытый переход в API mode при ошибке БД

Новый Direct-клиент всегда работает в единственном режиме DIRECT_MYSQL.

Ошибка подключения к БД должна отображаться как безопасная ошибка конфигурации/соединения, а не как просьба ввести IP backend.

Старый API-проект сохраняется отдельно как рабочий reference и rollback. Не удаляй его.

## 4. Точный функциональный контракт

### Авторизация

Таблица `__hr_typepos`.

Текущий backend НЕ использует `__hr_typepos_bf` для списка водителей или авторизации.

Поведение:

1. Первый запуск.
2. Автоматическая загрузка списка водителей.
3. Только водители с `access = 1`.
4. Выбор водителя.
5. Ввод пароля.
6. Сравнение `posTypeId`, `parol`, `access = 1`.
7. Локальная сессия без сохранения пароля.
8. При повторном запуске — проверка access.
9. Если доступ отключён — существующее состояние «Недоступно».

Пароли водителей не должны попадать в список, логи или постоянное хранилище.

Вход и access должны соответствовать backend contract; текущая схема аутентификации считается legacy и требует отдельной оценки безопасности перед rollout.

### Заказы

Источники:

- `reys` — Первый рейс.
- `reys_den` — Второй рейс.

Source-aware ID:

- `reys:<id>`
- `reys_den:<id>`

Только жёсткий allowlist источников.

Фильтрация по `date` и текущему `id_v`.

Состояния:

- `st_vv = 1` — сдано.
- `status = 2` — готово.
- `status = 1` — не готово.
- `col_s` — состояние количественной готовности, не самостоятельное количество накладных.
- `col` — количество накладных.

Три постоянных раздела:

- Первый рейс
- Второй рейс
- Сданные заказы

Сданные заказы остаются видимыми и переходят в третий раздел.

Сохранить существующую ручную сортировку и локальный порядок по водителю, дате и разделу.

Не изменять принцип отображения заказов без согласования.

### Адреса и контакты

Источники:

- `meneger_contr_ffl`
- `meneger_ffl`

Поиск по номеру заказа с TRIM.

Поддержать множественные адреса на один `nomer_z`.

Если кандидатов несколько, реализовать scoring/normalization строго по backend report.

Не выбирать автоматически первый результат при неоднозначности.

При отсутствии достоверного маршрута — «Ручной маршрут».

Поддерживать существующие схемы ссылок:

- HTTP / HTTPS
- yandexmaps
- yandexnavi

Сохранить открытие Яндекс Навигатора, копирование адреса, звонки клиенту, грузчику, менеджеру.

### Детали заказа

- Данные только заказа, принадлежащего текущему водителю.
- Маршрут и контакты через resolver.
- Время и комментарий из `vremya`.
- История максимум пяти предыдущих водителей из той же исходной таблицы.
- Сохранить извлечение телефонов из комментария на стороне Android.
- Не менять исходные данные при отображении.

### Кнопка «Сдал»

Это единственная необходимая бизнес-операция записи.

Транзакция:
1. Проверить текущий access.
2. Найти заказ по `id` и `id_v`.
3. Заблокировать строку через `SELECT ... FOR UPDATE`.
4. Если уже сдан — вернуть `already_delivered`.
5. Иначе установить только `st_vv = 1`, `date_att_log = NOW()`.
6. Проверить результат.
7. Commit либо rollback.

Запрещены любые незапрошенные изменения `status`, `col_s`, `col`, `sort_r` и других полей.

Никакого live write без явно одобренного безопасного тестового заказа.

### Уведомления

Сохранить polling-based second-route notifications, существующие Android receivers и поведение по нажатию уведомления.

Счётчики:
- Первый активный рейс.
- Второй активный рейс.
- Общее количество сданных.
- Source-aware IDs активных заказов второго рейса.

Не называть polling полноценным push.

Проверить ограничения Android на фоновые процессы.

### Телефонный справочник

- `nastroiki`: `karta`, `imya_karta`
- `phone`: `name`, `nomer_full`
- `__hr_typepos`: активные водители, mobile с fallback на whatsapp

Сохранить существующие экраны и действия копирования/звонка.

### route-opened

В backend это операция проверки/логирования без записи в MySQL.

В новой реализации сделать ownership validation + no-op, если report не содержит другого утверждённого способа хранения.

Не создавать таблицы журналирования самостоятельно.

## 6. Конфигурация и подключение

Для controlled development Direct MySQL конфигурация приходит из игнорируемого `local.properties` или из безопасно инжектируемых Gradle properties:

- DIRECT_MYSQL_HOST
- DIRECT_MYSQL_PORT
- DIRECT_MYSQL_DATABASE
- DIRECT_MYSQL_USER
- DIRECT_MYSQL_PASSWORD
- DIRECT_MYSQL_USE_SSL

Не выводить значения в отчётах, логах и UI.

Исследовать:
- Совместимость JDBC-драйвера с Android runtime.
- TLS, проверку сертификата и имени сервера.
- Таймауты подключения.
- Закрытие соединений.
- Конкурентность.
- Запросы только вне Main thread.
- Ошибки и повторные попытки.
- Возможность подключения из эмулятора и реального устройства.

Использовать параметризованные запросы.

НЕ считать `local.properties` защитой пароля внутри APK. BuildConfig или аналогичная упаковка делает секрет извлекаемым.

Не создавать production APK с admin/full-access DB account.

## 7. Обязательная модель безопасности

Очень важно: **Direct MySQL с общим DB-логином внутри APK не обеспечивает безопасность, эквивалентную backend.**

Даже если SQL содержит `WHERE id_v = ?`, пользователь модифицированного APK может выполнять другие допустимые для DB-аккаунта запросы.

Повторная проверка `access=1` в Android также не является серверным механизмом запрета.

Column-level UPDATE снижает ущерб, но не ограничивает запись заказами только одного водителя.

Особый риск — чтение `__hr_typepos.parol` через общую учётную запись DB.

Требования:
- Не использовать full-access credentials для распространения.
- Не открывать MySQL всему интернету.
- Подготовить модель угроз.
- Рассмотреть серверно-принудительное разграничение доступа: минимальный API на существующей инфраструктуре, DB-side stored procedures с корректно проверенной идентичностью, отдельные DB identities или другие проверяемые варианты.
- Не считать VPN или TLS заменой авторизации.
- Не заявлять production readiness, пока серверная изоляция прав водителей не доказана.

Если безопасный прямой доступ невозможно реализовать с текущими полномочиями, продолжать developer-only реализацию, но пометить DRIVER_ROLLOUT как BLOCKED_SECURITY.

Запрещено подменять это решение утверждением «раз логов нет и права ограничены — приложение безопасно».

## 8. Правила тестирования и отчётности

Каждый этап обязан содержать:

1. Конкретные изменённые файлы.
2. Что реализовано.
3. Что не реализовано.
4. Какие тесты действительно выполнены.
5. Какие команды запущены и их exit code.
6. Результат сборки.
7. Если использовалась БД — какое реальное чтение доказано без публикации чувствительных данных.
8. Если тест проводился на Android — какой именно APK установлен.
9. Что осталось непроверенным.
10. Результат этапа.

Статусы этапа:

- POSITIVE — все критерии этого этапа выполнены.
- NEGATIVE — тест/проверка провалены.
- BLOCKED — объективная зависимость недоступна.

Отдельно веди статусы:

- STATIC_CHECK
- UNIT_TEST
- BUILD
- EMULATOR_RUNTIME
- REAL_DEVICE_RUNTIME
- LIVE_DB_READ
- LIVE_DB_WRITE
- SECURITY_REVIEW

Не выдавать успешно собранный APK за подтверждённое подключение к БД.

Не выдавать unit-тест с mock JDBC за live MySQL test.

Не выдавать успешное появление списка на экране за доказательство, что строки пришли из production MySQL.

Если нет test driver/password, нельзя отмечать E2E login как PASS.

Если нет безопасного test order, нельзя проводить live write.

Если этап NEGATIVE или BLOCKED — остановиться, изложить причину. Не переходить автоматически к следующему этапу.

Промежуточная готовность реализации не равна готовности к публикации.

P8 — Уведомления и background polling.
P9 — Восстановление полного UI/UX и навигации.
P10 — Реальное end-to-end тестирование, APK и rollback.
P11 — Security review и оценка готовности к пилоту.

Для каждого этапа зафиксировать:
- Цель
- Какие файлы трогать
- Входные зависимости
- Что обязательно сделать
- Что запрещено
- Unit-тесты
- Runtime-проверки
- Acceptance criteria
- Stop conditions
- Точный формат отчёта

Дальше работать строго последовательно. Переходить к следующему этапу только при POSITIVE по текущему этапу.
