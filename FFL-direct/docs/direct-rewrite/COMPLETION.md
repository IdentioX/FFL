# Developer completion — 17.10.2026

Последнее указание пользователя отменяет prerequisite POSITIVE/STOP и разрешает довести приложение по усмотрению. Старые отчёты оставлены как история; недоступные live/device checks не становятся PASS. Новая реализация находится только в FFL-direct, package ru.ffl24.direct.dev, версия 0.2.0-dev.

## Поведение

- Вход: активные __hr_typepos, проверка пароля параметром, локальная identity без password/JWT, повторный access gate. Никакого backend IP/config flow.
- Рабочая дата видна над заказами; начальное значение — сегодня на телефоне. В настройках можно явно выбрать другую дату или вернуть «Сегодня». SQL не подменяет пользовательский выбор.
- Три вкладки: первый рейс, второй рейс, сданные из обеих таблиц. Компактные строки показывают номер, readiness, количество накладных, количественную готовность, клиента, адрес/примечание. Source ID сохраняется до деталей.
- Обновление — кнопка и pull-to-refresh. Точный backend SQL order — исходный порядок. Drag после долгого нажатия либо ↑/↓ задаёт локальный порядок driver/date/section. Новые строки добавляются в SQL order; удалённые/перенесённые удаляются из сохранённого порядка. «Сбросить порядок» сбрасывает overlay. Scroll driver/date/section сохраняется с задержкой250ms и при уходе; внезапный kill до commit может потерять последний сдвиг.
- Детали используют прежний P5 resolver/history. Переход из списка теперь подключён. Неоднозначный адрес не выбирается автоматически. Телефоны из комментария — помеченные предположения, целый raw text остаётся доступен. ACTION_DIAL никогда не делает автоматический вызов.
- «Сдал» доступна только ready + !delivered; в списке подтверждение через5секунд, в деталях обычное подтверждение. Проверки доступа/владельца и prepared SQL, FOR UPDATE, affected rows/postconditions/rollback, один write за раз. SET только st_vv/date_att_log. При неизвестном commit — сообщение об неизвестном результате; автоматического write retry нет. Смена session перед UPDATE/commit не публикует успех. Это клиентские проверки, не server row isolation.
- Справочник: карта/владелец из nastroiki, важные телефоны phone, активные водители __hr_typepos, mobile→whatsapp fallback. Raw directory phones не форматируются/split/dedupe. Copy и безопасный dial.
- Уведомления выключены по умолчанию. Включение требует Android permission. Unique periodic WorkManager request, сеть, минимум15мин; Android Doze/экономия/force-stop могут задерживать. Первый успешный summary — baseline без уведомления; seen IDs по driver/date не удаляются при доставке, поэтому повторного уведомления нет. Хранится только один текущий seen scope. Persist-before-notify предотвращает дубли после смерти процесса, но смерть между сохранением и notify может потерять уведомление. Одно агрегированное уведомление без клиентских имён/адресов; immutable PendingIntent ведёт во второй рейс только после совпадения текущего водителя и access gate. Logout/disabled/opt-out отменяют работу и уведомление. WorkManager manifest merger предоставляет reschedule/constraint receivers; отдельный always-on service не создаётся.
- Настройки: постоянная тема, рабочая дата, opt-in уведомления, выход. Реквизитов API/DB в водительском UI нет.

## Проверка и ограничения

Точные команды/результаты и APK SHA фиксируются в PROGRESS.md и evidence/completion. Unit SQL/JDBC proxies и Compose fixtures отдельно учитываются от настоящей MySQL. На собственном одноразовом стенде MySQL8.4.11/InnoDB проверены настоящий SELECT1 через Android JDBC/TLS, активные водители/пароль/access, обе таблицы/разделы, детали, справочник, summary, транзакция, идемпотентность и rollback после реального UPDATE. Production repositories подключены к настоящему экрану через test-only configuration: вход → список → детали → «Сдал» → контроль строки MySQL. Эта конфигурация и вымышленные данные отсутствуют в распространяемом main APK.

Рабочая legacy БД пользователя, её schema/types/grants/CA/auth compatibility, физический телефон, API24/36/minified runtime, реальные карты/звонки, измеренный15-minute/Doze/reboot не проверены. Ни одной production DB read/write не выполнялось. Разрешение на код не разрешает production write; DRIVER_ROLLOUT=BLOCKED_SECURITY сохранён. Общий DB account, даже с column grants, не обеспечивает серверного разделения водителей.

Сводка использует два последовательных SELECT как backend: при конкурентном изменении counts и ID list могут относиться к разным моментам. Уведомление строится только по фактическим ID, не по разнице counts. Следующая проверка исправляет отображаемую сводку; единый DB snapshot пока не обещается.

При пустой конфигурации текущий APK показывает «Подключение не настроено». Для настоящих данных необходима developer-сборка с DIRECT_MYSQL_* и явной CA через безопасные настройки среды/ignored local.properties по MYSQL_CONNECTION_LAYER.md. Пароли не передаются в чате или командной строке, не выводятся в логи. Без этих реквизитов нельзя честно объявить живую программу принятой на рабочей БД.
